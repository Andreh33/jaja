# Core Web Vitals: cómo medir una mejora sin confundirla con ventas

Una página puede verse bien en tu ordenador y responder peor en el móvil de otra persona. Los Core Web Vitals ayudan a describir partes de esa experiencia. Para utilizarlos con criterio, necesitas saber qué miden, de dónde proceden los datos y qué recorrido estás comprobando.

La referencia oficial reúne tres métricas: **LCP**, sobre la carga del contenido principal; **INP**, sobre la respuesta a interacciones; y **CLS**, sobre desplazamientos visuales inesperados. Los objetivos de buena experiencia son LCP de 2,5 segundos o menos, INP de 200 milisegundos o menos y CLS de 0,1 o menos, evaluados en el percentil 75 y separando móvil y escritorio. Puedes consultar su definición en [Web Vitals](https://web.dev/articles/vitals).

## No todas las mediciones responden a la misma pregunta

Una prueba de laboratorio sirve para investigar una página bajo unas condiciones concretas. Permite reproducir un cambio, comparar una versión y observar qué recursos o tareas pueden influir.

Los datos de campo describen experiencias recogidas de visitantes reales cuando existe muestra suficiente. No debes presentar una prueba aislada como si representara a todas las personas que utilizan la web. Si una herramienta no dispone de datos para una dirección, registra esa ausencia; no significa cero problemas ni una puntuación perfecta.

## Elige páginas que importen al negocio

La portada no representa todos los recorridos. Incluye una página de servicio, un artículo, una ficha de producto o la herramienta interactiva que utiliza el visitante. En cada caso, define una tarea: abrir la oferta, buscar una guía, seleccionar una variante o preparar un presupuesto.

Una animación no debería impedir leer el contenido o accionar un control. Cuando añadas juegos o herramientas, revisa cuándo cargan, qué ocurre al cerrarlos y cómo se comportan en una pantalla pequeña. El contenido principal debe seguir teniendo una ruta clara.

## Prepara una comparación reproducible

Antes de modificar la web, registra la URL, la versión probada, el dispositivo o emulación, las condiciones de red y la herramienta utilizada. Repite la prueba con una configuración equivalente tras el cambio.

Guarda también una observación funcional. Un resultado numérico puede mejorar mientras el formulario deja de validar un campo o una imagen importante desaparece. La verificación debe comprobar que la tarea sigue funcionando.

Para una interacción lenta, reproduce el paso concreto. Para una imagen que llega tarde, revisa cuál ocupa el contenido principal y cómo se solicita. Para saltos visuales, observa qué elemento cambia de tamaño o entra sin espacio reservado. El problema observado determina la corrección; no hace falta empezar sustituyendo toda la tecnología.

## Qué se puede afirmar después

Si dos pruebas equivalentes muestran un cambio, explica su alcance: qué página, qué versión y qué condiciones. Después comprueba si los datos reales disponibles evolucionan en la misma dirección.

Los ingresos necesitan otra medición. El número de visitas, la intención del público, la oferta o una campaña pueden cambiar a la vez que la web. Una mejora técnica no permite calcular por sí sola cuánto aumentarán las ventas. Evita publicar porcentajes que no puedas relacionar con registros comparables.

## Aplica este criterio a una experiencia propia

En [Latech Lab](/lab) puedes explorar juegos y herramientas. Su revisión incluye controles, pausas y continuidad, además de cómo se ven. Son aspectos de calidad que deben verificarse aunque no aparezcan resumidos en una única puntuación.

Si estás preparando una reforma, añade al [briefing](/briefing) las tareas que deben seguir funcionando y acuerda cómo comprobarlas. Una entrega útil combina evidencia técnica con una experiencia que la persona pueda completar.
